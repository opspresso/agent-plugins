# 스킬 행동 평가

스킬이 형식상 유효한지를 넘어, 필요한 때 로드되고 실제 결과를 개선하는지 확인한다.
평가기는 Agent Studio 밖의 개발 도구로 실행할 수 있다. 스킬 런타임에 shell이나 별도
모델 실행 능력이 있다고 가정하지 않는다.

## 평가할 때

다음 변경에는 행동 평가를 붙인다.

- 새 스킬 추가
- `description`의 트리거·제외 경계 변경
- 도구 선택이나 호출 순서 변경
- 출력 계약·보안 규칙 변경
- 실제 오작동을 고치는 회귀 수정

맞춤법처럼 판단을 바꾸지 않는 수정은 정적 검증으로 충분하다.

## Case 형식

case에는 문장 일치가 아니라 관찰 가능한 동작을 적는다.

```yaml
- id: diagram-positive-01
  prompt: "이 서비스의 요청 흐름을 한 장으로 그려줘"
  should_trigger: true
  expected_skill: diagram-design
  required_behaviors:
    - 구성 요소와 방향 관계를 표현한다
  forbidden_behaviors:
    - 화면 UI를 설계한다
  fixture: null
```

- `id`는 결과를 합칠 때도 유지한다. prompt를 key로 쓰지 않는다.
- `required_behaviors`는 결과에서 증거를 찾을 수 있게 쓴다.
- `forbidden_behaviors`는 실제로 일어나면 품질을 낮추는 행동만 넣는다.
- 특정 문장·heading·단어를 그대로 요구하지 않는다.
- 입력 fixture는 작고 결정적이어야 하며 외부 현재 상태에 기대지 않는다.

## 라우팅 평가

스킬마다 두 종류를 함께 둔다.

1. **Positive** — 표현이 달라도 분명히 이 스킬이 필요한 요청
2. **Near-miss negative** — 핵심 단어는 겹치지만 다른 스킬이나 일반 응답이 맡아야 하는 요청

쉬운 negative만 두면 description이 과하게 넓어져도 통과한다. 실제 충돌 상대의
description을 읽고 경계 case를 만든다. 예를 들어 `diagram-design`은 차트,
웹 화면, 일반 이미지 요청과 구분한다.

## 결과 품질 평가

결과 품질을 바꾸는 수정은 가능한 경우 같은 prompt를 두 조건에서 비교한다.

- 새 스킬과 스킬 없는 조건
- 수정 전과 수정 후

두 조건은 같은 모델·입력·도구 구성에서 독립된 context로 실행한다. 먼저 필수·금지
행동을 기계적으로 판정하고, 구조·명료성처럼 자동 판정하기 어려운 부분만 사람이 본다.
비교 조건 이름을 결과에 명시하고 디렉터리 정렬 순서로 기준과 후보를 추론하지 않는다.

## 실행과 실패 분류

- 결정적인 case는 한 번 실행한다. 출력 변동이 판정을 바꾸는 case만 반복한다.
- 반복한 case는 성공률과 분산을 함께 기록한다.
- timeout, 도구 부재, fixture parse 실패는 `INFRA_ERROR`로 기록한다.
- 평가 case가 0개이거나 결과를 읽지 못하면 전체 평가를 실패시킨다.
- 병렬 도구 호출이 나오면 모든 호출 결과를 해당 `tool_use_id`에 돌려준다.
- destructive tool은 평가에서 제외한다. 꼭 필요하면 격리된 환경과 별도 승인을 사용한다.

## 과적합 방지

수정에 사용한 case와 최종 확인 case를 나눈다. 최종 확인 case는 같은 의도를 다른 표현과
입력 크기로 묻고, 수정 과정에서는 보지 않는다. held-out 결과가 나빠지면 기존 case가
좋아졌어도 description을 채택하지 않는다.

## 완료 조건

- positive와 near-miss negative가 모두 기대대로 라우팅된다.
- 필수 행동이 충족되고 금지 행동이 나타나지 않는다.
- `INFRA_ERROR`를 스킬 실패나 성공으로 계산하지 않는다.
- baseline보다 나아진 점이 없으면 규칙을 더 늘리지 않는다.
- 남은 실패는 case id, 관찰된 결과, 다음 수정 범위와 함께 기록한다.
