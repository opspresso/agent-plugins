# 출력 형식

지적을 먼저 쓴다. 요약은 짧게 둔다.

## 지적이 있을 때

```markdown
**지적**

1. Critical — `path/to/file.ext:123` — 한 줄 제목
   무엇이 문제이고 어떤 조건에서 터지는지. 왜 중요한지.
   고치는 법: 구체적인 조치 한 줄.

2. Warning — `path/to/file.ext:45` — 한 줄 제목
   설명.
   고치는 법: 구체적인 조치 한 줄.

**리뷰 범위**

본 것: PR #1234의 변경 파일 8개. 렌즈: general-correctness, data-layer.
건너뛴 것: runtime-safety — 해당 신호가 diff에 없음.

**남은 위험**

[판정에 영향을 주는 미확인 파일·실행 경로·검증과 확인하지 못한 이유]
```

## 지적이 없을 때

```markdown
지적할 것이 없다.

본 것: PR #1234의 변경 파일 3개. 렌즈: general-correctness, tests-conventions.
검증: [직접 실행하거나 관측한 검사와 결과, 미실행이면 그 사실]
남은 위험: [실제 미확인 범위 또는 추가로 확인된 위험 없음]
```

## diff가 비었을 때

```markdown
이 대상에는 리뷰할 diff가 없다.

확인한 대상: PR #1234.
다음 할 일: 다른 PR 번호를 주거나 리뷰할 diff를 붙여 준다.
```

## 규칙

- 칭찬 절을 만들지 않는다.
- 긴 요약 아래에 지적을 묻지 않는다.
- 가능하면 파일과 줄 번호를 붙인다.
- 한 지적이 여러 파일에 걸치면 먼저 고쳐야 할 파일을 적는다.
- 사용자의 언어로 쓴다.
- 확인하지 않은 CI 결과를 통과했다고 말하지 않는다.
- 사용자가 GitHub 리뷰 판정을 요청하지 않았으면 "승인"이라고 쓰지 않는다.
- 연결된 `engineering-writing`이 있으면 문장을 다듬는 데 사용한다. 없으면 조건·영향·수정 방향을
  구체적으로 쓴다. 심각도를 형용사로 부풀리지 않고 실제 확인한 범위만 보고한다.
