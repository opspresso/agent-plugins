# 출력 형식

지적을 먼저 쓴다. 요약은 짧게 둔다.

## 지적이 있을 때

```markdown
**지적**

1. Critical — `path/to/file.ext:123` — 한 줄 제목
   무엇이 문제이고 어떤 조건에서 터지는지. 왜 중요한지.
   고치는 법: 구체적인 조치 한 줄.

2. Warning — `path/to/file.ext:45` — 한 줄 제목
   설명.
   고치는 법: 구체적인 조치 한 줄.

**리뷰 범위**

본 것: PR #1234의 변경 파일 8개. 렌즈: general-correctness, data-layer.
건너뛴 것: runtime-safety — 해당 신호가 diff에 없음.

**남은 위험**

생성 파일과 lock 파일 본문은 보지 않았고, 이전 리뷰 코멘트와 CI 상태는 읽지 않았다.
```

## 지적이 없을 때

```markdown
지적할 것이 없다.

본 것: PR #1234의 변경 파일 3개. 렌즈: general-correctness, tests-conventions.
남은 위험: 이전 리뷰 코멘트와 CI 상태를 보지 않았다.
```

## diff가 비었을 때

```markdown
이 대상에는 리뷰할 diff가 없다.

확인한 대상: PR #1234.
다음 할 일: 다른 PR 번호를 주거나 리뷰할 diff를 붙여 준다.
```

## 규칙

- 칭찬 절을 만들지 않는다.
- 긴 요약 아래에 지적을 묻지 않는다.
- 가능하면 파일과 줄 번호를 붙인다.
- 한 지적이 여러 파일에 걸치면 먼저 고쳐야 할 파일을 적는다.
- 사용자의 언어로 쓴다.
- 확인하지 않은 CI 결과를 통과했다고 말하지 않는다.
- 사용자가 GitHub 리뷰 판정을 요청하지 않았으면 "승인"이라고 쓰지 않는다.
- 문장은 `engineering-writing`을 따른다. 심각도를 형용사로 부풀리지 않는다.
