# HTML 와이어프레임

제품 질문 하나를 보고 고치고 이야기하기 쉬운 저충실도 HTML로 바꾼다. 이 산출물은 무엇이
화면에 들어가야 하는지와 작업이 어떤 순서로 흘러야 하는지를 정한다. 구조 검토에 집중하도록
시각적 완성도는 낮게 유지한다.

## 리뷰 질문을 먼저 정한다

대화, 받은 자료, 프로젝트 문서를 읽고 제품의 어휘·콘텐츠 모델·이미 정해진 제약을 그대로
쓴다. 충돌하면 위가 이긴다.

1. 사용자가 명시한 지시와 이미 합의된 결정
2. 제품의 기존 구조와 용어
3. 모델링하는 사용자, 작업, 콘텐츠
4. 모델 자신의 레이아웃 판단

만들기 전에 다음을 정한다.

- 사용자와 그가 끝내야 하는 일
- 검토 대상인 화면 또는 경계가 분명한 흐름 하나
- 반드시 들어가야 하는 정보와 행동
- 안전하게 가정해도 되는 것
- 이 와이어프레임이 답해야 할 구조적 질문

**실제 라벨과 대표 콘텐츠를 쓴다.** 저충실도는 익명 상자와 lorem ipsum 을 써도 된다는
뜻이 아니다. 문구 길이가 레이아웃을 바꾸므로 진짜 문장을 넣는다.

## 구조가 미정이면 방향을 비교한다

두셋을 만들되 **제품 결정이 다른 방향**이어야 한다.

- 내비게이션 모델
- 묶는 방식과 순서
- 주요 행동의 위치
- 콘텐츠 밀도
- 한눈에 보는 개요 대 단계별 진행
- 데스크톱에서 모바일로 접히는 방식

색을 바꾸거나 카드를 재배치한 것은 별개 방향이 아니다. 방향마다 짧은 이름과 트레이드오프
한 문장을 붙인다. 핵심 콘텐츠와 작업은 방향들 사이에서 같게 유지한다.

가능하면 **한 파일에 담고** 키보드로 조작되는 작은 선택기로 전환한다. 여러 파일로 나누면
리뷰어가 비교를 못 한다. 사용자가 이미 구조를 정했다면 그 방향 하나만 만든다.

선택기는 **리뷰 도구이지 제품의 일부가 아니다.** 회색조로 눌러 놓은 지면에서는 제품의
내비게이션과 구분되지 않으므로, 와이어프레임 바깥에 이름을 붙인 별도 영역으로 두고
(`<nav aria-label="방향 선택">` 같은) 리뷰용이라고 라벨을 단다. 방향 이름과 트레이드오프도
그 영역에 둔다.

## 의도적으로 미완성으로 둔다

- 회색조 팔레트, 시스템 폰트, 단순한 테두리, 평범한 블록을 쓴다.
- 브랜드색, 그라데이션, 그림자, 일러스트, 장식 이미지, 다듬은 컴포넌트 스타일을 쓰지 않는다.
- radius 와 간격을 절제한다. 위계를 판단할 만큼의 질서만 두고 그 이상 다듬지 않는다.
- 이미지와 미디어는 라벨을 붙인 자리표시자로 둔다. 그 자산이 구조 결정을 바꿀 때만 예외다.
- 주석은 직접 보여 줄 수 없는 가정, 열린 질문, 동작을 드러낼 때만 단다.

**미완성과 허술함은 다르다.** 간격이 제멋대로거나 글자가 안 읽히거나 좁은 화면에서 깨지는
것은 저충실도가 아니라 결함이다.

## 동작은 리뷰에 필요한 만큼만

- 내비게이션·펼침·짧은 작업 흐름을 검증할 때만 클릭스루를 넣는다.
- 네이티브 컨트롤을 쓰고 키보드 포커스를 보이게 둔다.
- 애니메이션, 영속화, 가짜 API, 상태 관리 라이브러리를 넣지 않는다.
- 리뷰 목적이 없는 컨트롤은 지우거나 범위 밖이라고 라벨을 단다.

## 빌드 계약

자체 완결 HTML 하나로 낸다. CSS 와 JavaScript 를 전부 인라인하고 빌드 도구나 외부
서비스를 요구하지 않는다.

- **바깥으로 요청하지 않는다.** 웹폰트, CDN, 원격 이미지, `fetch` 전부.
- **저장소와 부모 창을 건드리지 않는다.** `localStorage`·`sessionStorage`·쿠키·`window.parent`
  는 격리된 환경에서 제한될 수 있다. 상태는 DOM 안에서만 다룬다.
- **링크는 문서 안(`#id`)이나 절대 주소로.** 상대 경로는 파일이 놓이는 위치에 따라 깨진다.
- 시맨틱 landmark, heading, 목록, form, button 을 쓴다.
- 넓은 데스크톱과 좁은 모바일에서 모두 쓸모 있게 만들고 page body 에 가로 스크롤이
  생기지 않게 한다.
- 사용자가 입력한 문자열을 화면에 다시 그릴 때 `innerHTML` 로 붙이지 않는다.
- 자리를 채우려고 원본에 없는 제품 범위를 지어내지 않는다.

## 참고 스킬이 없을 때

`frontend-design`의 상세 카탈로그는 그 스킬이 현재 런에 제공될 때만
`Skill(skill_name="frontend-design", file_path="references/ai-visual-tells.md")`로 읽는다.
제공되지 않으면 이 스킬의 인라인 규칙과 자체 참고 파일로 진행한다.
같은 플러그인에 있다는 이유로 다른 스킬의 파일을 현재 스킬 경로에서 찾지 않는다.

## 산출

**이번 런에 `SaveFile`이 있으면 그것으로 낸다.** `mime_type`은 `text/html`, `content`는 완성된
HTML 전문, `name`은 내용을 알아볼 수 있는 이름이다. 파일은 따로 전달되므로 답변에 본문을 다시 붙이지 않는다.

`SaveFile`이 없으면 완성된 HTML 전문을 `html` 코드 블록 하나로 주고, `.html`로 저장해서
열면 된다고 알린다. 이때 파일을 만들었다고 말하지 않는다.

## 핸드오프

- 방향들의 이름과 각각의 트레이드오프 한 문장
- 이 단계에서 일부러 미룬 시각 결정 — 색, 활자, 컴포넌트 스타일, 모션
- 실제로 확인한 렌더링 조건과 확인하지 못한 화면 크기·브라우저

lorem ipsum, 죽은 버튼, 백엔드 용어를 그대로 쓴 라벨 같은 콘텐츠 티의 목록은 같은
플러그인의 `frontend-design` 스킬 안에 있다 — **그 스킬을 열면 그 디렉터리의**
`references/ai-visual-tells.md`다. 시각 항목은 이 스킬의 저충실도 계약이 먼저다.

## 기존 파일 수정과 저장 한도

기존 HTML·SVG 파일 ID와 `File`이 있으면 원본을 `inspect`로 읽는다. HTML의 `read`는
활성 내용을 제거하므로 코드 보존 편집에는 원문을 반환하는 `inspect`를 사용한다.
요청한 부분은 `File(operation="edit", file_id="<실제 ID>", edits=[...])`로 수정한다.
각 편집은 `operation="replace_text"`, `part="text"`, `index=0`, 한 번만 등장하는 원문
`text`와 `replacement`를 사용한다. 원본을 유지한 새 파일 ID가 반환된다.
잘린 원문으로 전체 파일을 재작성하지 않으며 수정 후 새 ID를 검사해 변경을 대조한다.
텍스트 검사는 `from`으로 이어 읽을 수 없다. 잘림으로 수정 대상이 보이지 않으면
원문을 추측하지 않고 접근 한계와 미수행 범위를 알린다.

`SaveFile`의 파일당 한도는 UTF-8 1MiB다. `SaveFile`과 `File` 생성·편집은 런당 합계
10회 시도를 공유하며 실패도 차감된다. 한도에 도달하면 같은 런에서 분할·재호출을
계속하지 않고 전달한 파일과 남은 작업을 밝힌다.
