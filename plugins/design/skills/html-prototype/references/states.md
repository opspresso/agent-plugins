# 상태 모델

프로토타입을 짜기 전에 상태를 표로 적는다. 먼저 적으면 만들다 상태를 빠뜨리지 않고,
무엇을 일부러 뺐는지가 기록으로 남는다.

## 표 포맷

| 상태 | 트리거 | 보이는 결과 | 가능한 행동 |
|---|---|---|---|
| 차단됨 | iOS 스모크 테스트 실패 | 실패한 검사와 차단 사유가 보인다 | 재실행 기록 |
| 저장 중 | 재실행 결과 제출 | form 과 트리거가 비활성, 진행 상태를 알림 | 대기 |
| 저장 실패 | 저장이 거부됨 | 입력값을 유지한 채 실패 이유와 재시도를 보여 준다 | 재시도, 취소 |
| 준비됨 | 검사 4개가 모두 통과 | 요약이 4/4 로 바뀌고 릴리스 행동이 활성 | 릴리스 요청 |
| 요청됨 | 활성화된 릴리스 행동 선택 | 실제 릴리스 시스템이 이어받는 지점을 설명한다 | 설명 닫기 |
| 비어 있음 | 검토 메모가 하나도 없음 | 메모가 없다는 사실과 무엇을 하면 되는지 | 메모 추가 |

행 하나가 화면 하나가 아니다. 같은 화면의 다른 국면이어도 위 네 칸이 다르면 별개 행이다.

## 어떤 상태를 뺄 수 없는가

| 화면에 이것이 있으면 | 이 상태가 필요하다 |
|---|---|
| 비동기로 보이는 동작 | 진행 중, 성공, 실패와 복구 |
| 목록이나 컬렉션 | 비어 있음 |
| 잠긴 행동 | 왜 잠겼는지 |
| 입력 form | 검증 실패, 제출 중, 제출 후 |
| 바깥에서 오는 데이터 | 로딩, 부분 실패 |
| 권한이 갈리는 화면 | 볼 수 없음과 볼 수는 있으나 바꿀 수 없음의 구분 |
| 좁은 화면 | 주요 작업이 유지되는 모바일 구성 |

시나리오가 도달하지 못하는 상태를 체크리스트 때문에 끼워 넣지 않는다. 빼기로 했으면
핸드오프에 적는다.

## 상태마다 정할 것

- **무엇이 바뀌는가** — 문구, 활성/비활성, 영역 교체 중 무엇인지.
- **색 말고 무엇으로 알리는가** — 아이콘, 라벨, 위치, 테두리 굵기.
- **알림이 필요한가** — `aria-live` 나 `role="status"` 로 스크린리더에 전달할 변화인지.
- **focus 가 어디로 가는가** — 특히 dialog 를 닫은 뒤와 영역을 교체한 뒤.
- **되돌릴 수 있는가** — 되돌릴 수 없으면 실행 전에 확인을 받는지.

## 흔한 실수

- 로딩은 있는데 실패가 없다. 비동기는 실패할 수 있으니 그것이 상태다.
- 실패 후 입력값이 날아간다. 오류는 값을 지키면서 이유를 말해야 한다.
- 비활성 버튼이 이유를 말하지 않는다. 왜 못 누르는지가 화면에 있어야 한다.
- 빈 상태가 "데이터 없음" 한 줄이다. 무엇을 하면 채워지는지 적는다.
- 성공 알림만 뜨고 화면의 값이 그대로다. 상태 변화가 화면에 반영돼야 한다.
- 오류 문구가 사과만 한다. 무엇이 실패했고 무엇을 하면 되는지 쓴다.
