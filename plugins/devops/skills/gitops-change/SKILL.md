# GitOps 변경

GitOps가 관리하는 리소스는 저장소와 배포 파이프라인을 통해 변경한다. 클러스터에 직접 넣은
변경은 다음 sync에서 되돌아가거나 desired/live 차이를 남길 수 있다.

## 대상과 정책 확인

1. 요청한 변경, 환경·phase·클러스터와 종료 조건을 확인한다. 조사, 파일 수정, PR 생성과 배포 확인을 구분한다.
2. Application/ApplicationSet의 source, revision, values 적용 순서와 sync 정책을 읽는다.
3. 대상 저장소의 지침, README, chart와 배포 workflow를 확인해 고칠 파일과 값의 소유자를 찾는다.
4. 변경 전후 값, 영향 범위, 필요한 검증과 되돌리는 방법을 정리한다.

아래 구조는 `argocd-env-demo`의 예시다. 실제 파일과 정책을 확인한 뒤 적용한다.

```
charts/<project>/
  values.yaml                 # 공통 값
  values-<phase>.yaml          # phase 값; 일부 값은 배포 파이프라인이 갱신
  <env>/values-<cluster>.yaml   # 클러스터 값
apps/<name>.yaml               # ApplicationSet
```

| 변경 범위 | 확인할 파일 |
|---|---|
| 모든 환경 | `charts/<project>/values.yaml` |
| 한 phase | `charts/<project>/values-<phase>.yaml` |
| 한 클러스터 | `charts/<project>/<env>/values-<cluster>.yaml` |
| 새 앱 | `apps/<name>.yaml`와 `charts/<name>/` |

values의 실제 덮어쓰기 순서를 확인하고 요청 범위를 표현하는 가장 좁은 파일을 수정한다.
상위 공통 값을 바꾸거나 하위 override에 가려지는 변경을 만들지 않는다.

## 이미지와 배포 경로

이미지 버전은 누가 갱신하는지 먼저 확인한다. `repository_dispatch` 등으로 phase values를
갱신하는 환경에서는 파이프라인을 사용한다. 생성되는 값을 직접 고쳐 다음 배포에 덮이게 하지 않는다.
이미지 변경 요청을 임의의 workflow 실행이나 다른 환경의 배포 권한으로 확대하지 않는다.

`argocd-env-demo`의 배포 workflow는 prod를 PR로, 다른 phase를 main 반영으로 처리할 수 있다.
이 파이프라인 동작을 수동 작업의 직접 커밋 허가로 해석하지 않는다. 수동 변경의 브랜치·PR 정책은
현재 저장소 지침과 사용자에게 받은 권한을 따른다.

## 변경과 PR

1. 현재 파일 내용을 읽고 필요한 값만 수정한다. 무관한 변경과 사용자 작업을 섞지 않는다.
2. 저장소에서 정한 lint·템플릿 렌더링·검증 절차를 확인하고 사용할 수 있는 도구로 수행한다.
   렌더링 결과에서 대상 리소스, 값의 타입과 다른 환경에 미치는 영향을 확인한다.
3. 허가된 경우 작업 브랜치에 커밋하고 PR을 만든다. 커밋·푸시·PR 생성 권한은 각각 요청 범위로 판단한다.
4. 변경 파일, 검증 결과와 PR URL을 전달한다. 실행하지 못한 검사는 이유와 함께 남긴다.

원격 작업에는 연결된 github MCP의 실제 schema를 사용한다. 도구가 없으면 변경 파일 경로,
패치나 최종 내용과 PR 초안을 제공한다. 없는 도구를 가정하거나 반영하지 않은 변경을 완료로 보고하지 않는다.

추가 권한이 필요한 작업은 최종 변경안과 영향을 보여 준 뒤 요청한다. 이미 허가된 작업을 다시 묻지 않는다.
PR 생성 요청만으로 머지·배포·Argo sync를 실행하지 않는다.

## 본문

연결된 `pr-description`이 있으면 사용한다. 없으면 변경 값과 파일, 이유, 환경·재시작 영향,
검증과 되돌리는 방법을 적는다. 한 PR에 한 목적을 담고 확인한 사실과 예상 영향을 구분한다.
“설정 최적화” 대신 “memory limit을 512Mi에서 1Gi로 변경한다”처럼 구체적인 값과 대상을 쓴다.

## 반영 확인

배포 확인까지 요청받았다면 다음 순서로 확인한다.

1. 저장소에 원하는 변경이 반영됐는가.
2. Argo CD가 해당 revision을 sync했는가.
3. Kubernetes의 실제 리소스와 rollout이 예상 상태인가.
4. 지표·로그나 해당 기능 확인으로 의도한 효과가 관측되는가.

단계별로 확인된 상태를 보고한다. PR 생성까지만 요청받았으면 이후 반영 확인 항목을 남긴다.
일부 단계의 도구가 없으면 관측하지 못한 범위를 밝힌다.

## 되돌리기와 예외

- 원복도 GitOps 경로로 처리한다. revert가 데이터·스키마·외부 상태까지 복구하는지 별도로 확인한다.
- 실제 `prune: true` 설정에서 리소스 정의를 삭제하면 클러스터 리소스도 삭제될 수 있다.
  삭제 대상과 데이터·서비스 영향을 먼저 확인하고 명시적으로 허가된 범위에서만 실행한다.
- 긴급 직접 변경은 사용자가 해당 조치를 명시적으로 요청한 경우에만 검토한다. sync 충돌, 영향과
  복구 방법을 확인하고 임시 변경 내역과 저장소에 반영할 후속 작업을 남긴다.
